# Release acceptance for 0.2.0

Manual desktop checks on 2026-10-15 used live Pi sessions on Windows and WSL. The user confirmed streaming, completion without a persistent spinner, recovery after a tool error, matching replies in Pi and desktop, subsequent messages, multiple desktop windows, parallel Windows/WSL activity, and sidebar order updates. iOS remains optional and untested.

During these checks, desktop twice retained an executed request in its local follow-up queue and blocked the next message before `turn/start` reached Pi. Closing extra windows did not immediately clear it. The queue later recovered; subsequent checks with one and multiple windows passed. The original client-side cause is unresolved. A daemon restart clearing the symptom is not proof of a fix.

An isolated regression reproduced a separate recovery defect: rebuilding history from JSONL discarded client message IDs and replaced live turn and user item IDs. Turn receipts now preserve these associations through the existing Pi writer. Tests reopen real isolated JSONL without an owner snapshot and check message identities. This corrects that demonstrated defect; it does not establish the cause of the earlier desktop queue stalls.

After the receipt update was loaded, a second message stalled again while the preceding completed request remained `sending` in the desktop queue. The server was idle and retained the matching client message ID in its persisted receipt. Identity preservation therefore does not resolve the desktop queue stall. Desktop logs showed a successful `turn/start` response followed by repeated owner changes between two clients. The connection between these ownership transitions and the stalled submission still needs verification.

Keep publication pending until the queue issue is resolved or its remaining uncertainty is explicitly accepted. The [queue probe](desktop-queue-diagnostics.md) is unavailable in the production desktop because DevTools are disabled; use existing logs and read-only server metadata. Do not resend an uncertain command automatically.

Publication now avoids repeated `thread/started` announcements for activity-only changes to already announced, loaded threads. The installed desktop turns those announcements into full ownership snapshots. Regression tests fail on the prior implementation for both idle and active threads and pass with title notifications and current catalog timestamps preserved. Live acceptance is still pending; this change does not clear an existing stalled desktop queue.

The next manual check stalled again. Read-only inspection found one client message ID in two completed server turns, while the next message had not reached Pi. Previously executed entries remained pending in saved desktop state. The earlier empty saved queue snapshot was insufficient evidence that the open windows had cleared their queues. Duplicate suppression now checks live accepted input and persisted receipts before invoking Pi; the desktop queue stall remains unresolved.

After an explicitly authorized full Desktop restart and loading duplicate suppression in both daemons, the user confirmed two sequential WSL submissions both received replies. Server history showed separate completed turns with distinct client message IDs, and the server returned to idle. This verifies that the current post-restart path works. It does not establish that the ownership race cannot recur. Desktop was restored to a normal launch; neither diagnostic listener was available.

The restart also exposed a separate native endpoint discovery failure. Desktop-owned browser transports share the app-tools pipe prefix but reject `tools/list`. Discovery now preflights capabilities, ignores these transports, and resolves the unique app-tools endpoint. Restarting only the managed sidebar worker restored `connected` status with no failed hosts or additional chat moves. Pi owners and daemon connections remained running during that worker update.

The subsequent two-window check also passed. The user opened the same WSL chat in both windows, sent two sequential messages from the second window, and sent another from the first. All three received replies. Server history showed three separate completed turns with distinct client message IDs; the server was idle and the persisted queue was empty. Desktop logs recorded one renderer owner and one follower, without the previous competing-owner transitions during this run. Together with the preceding pair, five post-restart submissions passed.

The current post-restart manual path passes. The isolated Desktop ownership defect and the exact cause of the earlier live state remain open; no claim is made that duplicate suppression repairs Desktop ownership. Keep this distinction when deciding whether to accept the remaining release uncertainty. The full local verification passed 192 tests, build, clean package installation, CLI loading, extension loading, and migrations.
